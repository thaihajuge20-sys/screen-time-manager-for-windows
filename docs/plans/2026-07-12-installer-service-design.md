# Screen Time Manager 安装与守护服务设计

## 目标

把现有免安装的 Windows 托盘程序改造成可正常安装的软件，并通过 Windows 系统服务实现可靠开机启动和前台程序异常退出后的自动恢复。

本次成功标准：

1. 用户得到一个标准 `Setup.exe`，可安装、升级和卸载。
2. 安装后系统服务随 Windows 启动，不依赖“启动应用”列表。
3. 用户登录后，服务在该用户的桌面会话启动原有托盘程序。
4. 用户从任务管理器结束前台程序后，服务会再次启动它。
5. 正常卸载会停止并删除服务、删除程序文件，可选择保留用户数据。
6. 文档明确说明：拥有管理员权限的人仍可停服务、改系统权限或卸载软件，软件无法对 Windows 管理员提供绝对防篡改保证。

## 已确认的现状

- 项目是 Rust 编写的 Windows GUI 程序，入口为 `src/main.rs`。
- 当前发布物是 ZIP，其中包含主程序以及 PowerShell/批处理安装脚本。
- `install.ps1` 只为当前用户创建登录时运行的计划任务。
- 主程序和托盘、窗口、数据库、Telegram 功能都运行在同一个交互式进程中。
- Windows 服务运行在 Session 0，不能直接承载现有托盘和遮罩窗口，因此必须将守护服务与前台程序分开。
- 上游仓库没有 `AGENTS.md`、架构文档或 `graphify-out/`。本设计以源码、安装脚本、README 和发布工作流为事实依据，不刷新 Graphify。

## 选定架构

采用“一个二进制、两种运行模式”：

- 默认模式：保留现有前台托盘程序行为。
- `--service` 模式：作为 Windows 服务运行，监视交互式用户会话并启动前台程序。

选择同一二进制可以减少发布文件、版本同步和安装复杂度。服务模式不初始化数据库、托盘、遮罩或 Telegram，只负责前台进程生命周期。

服务启动后：

1. 向 Windows Service Control Manager 报告运行状态。
2. 找到当前活动的交互式用户会话。
3. 使用该会话的用户令牌启动同一路径下的前台程序。
4. 等待前台进程退出；如果服务仍在运行，则经过短暂退避后重新启动。
5. 收到服务停止命令后停止拉起新进程，并结束本次守护循环。

首版只支持一台家用电脑上的当前活动会话，不扩展为企业多会话管理系统。

## 安装程序

使用 Inno Setup 生成签名友好的 `Setup.exe`：

- 默认安装到 `{autopf}\Screen Time Manager`。
- 复制 `screen-time-manager.exe`、许可证和必要说明。
- 安装阶段以管理员权限注册自动启动服务。
- 服务账号使用 `LocalSystem`，启动类型为 Automatic。
- 配置服务失败恢复策略，服务异常退出时由 Windows 重启服务。
- 升级时先停止服务，替换文件后重新注册/启动。
- 卸载时停止并删除服务，然后删除程序文件。

不再把计划任务作为默认安装路径；旧脚本会调整为兼容迁移或改为引导使用安装程序，防止同一程序被启动两次。

## 防轻易禁用边界

本次解决的是“孩子在任务管理器结束前台程序，软件就永久失效”：前台程序退出后由 SYSTEM 服务重新拉起。该服务不会出现在 Windows 的普通“启动应用”禁用列表中。

不会实现隐藏进程、rootkit、内核驱动、阻止管理员工具、伪装系统组件或不可卸载机制。孩子既然拥有管理员权限，仍可通过服务管理器、管理员终端、修改权限或卸载程序使其失效。若需要更强保证，产品层面的正确措施是把孩子账号改成标准用户，并由家长保管独立管理员账号。

## 错误处理与日志

- 服务启动、会话发现、前台启动、前台退出和停止事件写入 Windows Event Log 或项目自己的受限日志目录。
- 找不到活动会话时不报致命错误，定时重试。
- 前台程序连续快速退出时使用有上限的退避，避免形成高频重启循环。
- 服务停止必须有确定的退出路径，保证安装升级和卸载不会卡住。
- 日志不记录密码、Telegram token 或其他敏感配置。

## 测试策略

按照 TDD 实施：

1. 把“参数决定运行模式”和“重启退避判断”写成纯 Rust 逻辑，先写失败测试再实现。
2. 为安装脚本增加静态验证，检查安装、升级、卸载和服务参数是否完整。
3. GitHub Actions 在 Windows runner 上执行 `cargo test` 和 release build。
4. Windows 集成验证安装包可安装，服务为 Automatic/Running，登录后前台程序存在。
5. 手动结束前台进程，验证服务在规定时间内重新启动它。
6. 执行卸载，验证服务和程序文件被删除。

当前 Mac 没有安装 `cargo`，首次基线命令停在 `command not found`，并未运行到项目编译或测试。Windows 专用 API 和安装包必须以 Windows CI/实机结果作为最终证据。

## 发布与事实边界

代码修改、提交、推送、PR、合并、Windows 构建、安装包产出和 Windows 实机验证分别报告，不合并成一个“已完成”。本次用户只要求下载和改造，未经额外授权不会推送到远端、创建 PR、部署服务器或发布 GitHub Release。

这个项目没有后台服务部署需求。项目规则要求改动时查看服务器日志，但当前仓库没有服务器地址、后台组件或日志入口；不会为了形式要求连接无关服务器。若后续引入远程后台，再按其架构和凭据边界执行日志检查。
